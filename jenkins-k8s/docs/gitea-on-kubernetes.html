01 — The Problem

The repo that only lives on one machine

The pulse repository holds every Jenkins pipeline and every shared script the CI infrastructure depends on — llm-analysis.sh, extract-build-errors.sh, signing scripts, Helm charts. It lives as a plain directory on a single Linux host.

When a Mac Mini build agent needs those scripts, it has to already know where they are. Every Jenkinsfile carries a resolver loop — a patch stitched over a structural gap. The repo is manually cloned once and left to drift. One missed git pull and builds fail in ways that are genuinely hard to trace.

The PULSE_DIR resolver isn't the problem — it's the symptom. There is no authoritative, network-accessible source of truth for the repository.
fig. 1 — current state: local-only repo, manual sync, fragile paths

Without Gitea

  • Repo lives on one host only
  • Agents clone manually, once
  • No pull = stale scripts = silent failures
  • PULSE_DIR loop in all 6 Jenkinsfiles
  • New agent = manual bootstrap step
  • No webhook = no auto-trigger on push

With Gitea

  • Single HTTP URL for every agent
  • Clone fresh each build — always current
  • No drift, no stale scripts
  • PULSE_DIR resolver deleted from all pipelines
  • New agent just needs the URL and a token
  • Webhook fires Jenkins on every push
02 — The Tool

Gitea — a 60 MB Git server

Gitea is a self-hosted Git service written in Go. The entire server is a single binary, consumes 60–80 MB of RAM at rest, and exposes a GitHub-compatible API. It runs as a single Kubernetes pod backed by a 5Gi PVC.

Unlike GitLab — which requires multiple services and multi-gigabyte images — Gitea uses SQLite on a small volume and handles a private team's repositories with no noticeable resource footprint next to Jenkins.

03 — The Architecture

Every node connected through Tailscale

Gitea runs inside the existing Kubernetes cluster on the cylon host. It gets a ClusterIP service for Jenkins (same cluster, no network hop) and a NodePort 30300 for everything outside — Mac Mini agents, developer laptops — all reachable through the existing Tailscale mesh at 100.89.50.27:30300.

fig. 2 — gitea in kubernetes: nodes, pods and tailscale connections

The Mac Mini agents never touch cylon's filesystem. They talk to Gitea's HTTP endpoint — the same URL, always available, always at the latest commit. Jenkins uses Gitea's webhook to start builds the moment a push lands.

04 — The Flow

One push, full pipeline

Once Gitea is running, the developer experience reduces to a single gesture: git push. Everything downstream is automatic and deterministic.

①②③④⑤ sequence steps
  1. ①
    Developer pushes to Gitea

    Standard git push origin master to the Gitea remote. Gitea stores the commit and immediately fires the configured webhook.

  2. ②
    Gitea fires the webhook

    An HTTP POST hits Jenkins at jenkins-svc:8080/github-webhook/ — same cluster, sub-millisecond. No polling, no timer.

  3. ③
    Jenkins triggers the pipeline

    The pipeline job starts and dispatches stages — Mac Mini for iOS builds, cylon pod for Android and DevSecOps.

  4. ④
    Agents clone pulse from Gitea

    Instead of the PULSE_DIR resolver, every agent uses http://100.89.50.27:30300/dk/pulse. Always current. --depth 1 keeps it fast.

  5. ⑤
    Build runs, artifacts produced

    IPA or APK archived, LLM analysis runs, failure or success email sent. Pipeline logic is identical to today — only script-sourcing changed.

05 — Deployment

Up in under ten minutes

step 1 — add the helm repo
helm repo add gitea-charts https://dl.gitea.com/charts/
helm repo update
step 2 — gitea-values.yaml
# Minimal config for a private single-team setup
gitea:
  admin:
    username: dk
    password:  "changeme-on-first-login"
    email:     "dk@pulse.local"

service:
  http:
    type:     NodePort
    port:     3000
    nodePort: 30300   # reachable at 100.89.50.27:30300 via Tailscale

persistence:
  enabled:      true
  size:         "5Gi"
  storageClass: "standard"

resources:
  requests: { memory: "128Mi", cpu: "100m" }
  limits:   { memory: "256Mi", cpu: "500m" }

postgresql:    { enabled: false }   # use SQLite — fine for a small team
postgresql-ha: { enabled: false }
step 3 — install
helm install gitea gitea-charts/gitea \
  --namespace utilities \
  --create-namespace \
  --values gitea-values.yaml

kubectl rollout status deployment/gitea -n utilities
step 4 — push the pulse repo
# Create repo via API
curl -s -u dk:changeme-on-first-login \
     -X POST http://100.89.50.27:30300/api/v1/user/repos \
     -H "Content-Type: application/json" \
     -d '{"name":"pulse","private":true}'

cd ~/Documents/git/pulse
git remote add gitea http://dk:token@100.89.50.27:30300/dk/pulse.git
git push gitea master
step 5 — configure webhook in gitea
# Settings → Webhooks → Add Webhook → Gitea
# Target URL (ClusterIP, internal):
http://jenkins.utilities.svc.cluster.local:8080/github-webhook/

# Trigger on: Push events
step 6 — replace pulse_dir resolver in jenkinsfiles
# Replace the resolver loop with a single git clone
git clone http://dk:token@100.89.50.27:30300/dk/pulse.git \
    --depth 1 --single-branch --branch master \
    /tmp/pulse-$$

bash /tmp/pulse-$$/jenkins-k8s/shared/llm-analysis.sh

# No PULSE_DIR loop. No stale clone. No manual sync.
06 — After

What changes, what stays the same

The six Jenkins pipelines don't change structurally. The stages, email logic, LLM analysis — all stay identical. The only change is how agents find the shared scripts: from a fragile filesystem path to a stable HTTP URL.

New agents are trivial to onboard. Give them the Gitea URL and a read token. They clone on demand, always getting the latest version. The PULSE_DIR loop disappears from every pipeline.

Gitea is not a migration. It is a namespace declaration — a statement that this repository has an authoritative address on your network, and everything that needs it knows where to find it.
